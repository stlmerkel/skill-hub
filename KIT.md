# skill-hub kit manual

skill-hub is not a marketplace itself: it is the scaffolding for yours, and everything that identifies your hub lives in one config file, `hub.yml`.

## What you get

| Piece | What it does | Status |
|---|---|---|
| **Skill contract** | Each skill is a folder under `skills/` with a `SKILL.md` that follows the [Agent Skills specification](https://agentskills.io/specification), so it installs in any client that reads the spec | Available |
| **QA guard** | `skill-hub qa` checks your hub config and every skill: valid frontmatter, a name that matches its folder, a SemVer version, Python that compiles, and no committed secrets. It runs locally and on every pull request | Available |
| **Semantic releases** | Conventional commits (`feat:`, `fix:`) drive version bumps and changelogs through [Release Please](https://github.com/googleapis/release-please), one version per skill | Available |
| **Marketplace page** | `skill-hub build` turns your skills into a static, self-contained page and a `catalog.json`, restyled from `hub.yml` or replaced by your own theme. Host it anywhere | Available |
| **Client install paths** | Every skill installs into Claude Code, GitHub Copilot or Cursor by one documented command, from manifests `skill-hub manifests` generates from `hub.yml` | Available |
| **Deploy** | On every push to `main`, CI publishes the marketplace page to the deploy target `hub.yml` names: GitHub Pages, an S3-compatible bucket or your own server over rsync. Add your own target with one workflow file | Available |
| **Skill scaffolding** | `skill-hub new-skill <name>` creates a skill that already passes QA | Available |

## Quick start

You need [uv](https://docs.astral.sh/uv/). It installs a matching Python for you, and there is no Node toolchain.

```bash
git clone <your copy of this repo> my-hub
cd my-hub
uv sync
uv run skill-hub qa
```

A fresh clone passes with two warnings. They are reminders to make the hub yours:

1. **Edit `hub.yml`.** Set `hub.name` (lowercase letters, digits and single hyphens), `display_name`, `owner`, `description` and `repo_url`. Every skill-hub command reads identity from this file and nowhere else. The name, owner and description also feed the marketplace manifests, so run `uv run skill-hub manifests` after editing them.
2. **Replace the example skill.** `skills/example-skill/` shows the shape of a skill. Create your own with `uv run skill-hub new-skill <name>`, then delete the example once you have real skills. QA warns (S14) until you replace the new skill's placeholder description.
3. **Run `uv run skill-hub qa` again.** With no warnings left, your hub is ready for skills.

## Layout

```text
hub.yml                    your hub's identity and QA options (yours to edit)
skills/<skill>/SKILL.md    your skills, one folder each (yours)
skills/<skill>/...         optional scripts/, references/, assets/
skill_hub/                 the QA tool (part of the kit)
skill_hub/themes/default/  the built-in marketplace theme (copy it to make your own)
site/                      build output from skill-hub build (git-ignored)
tests/                     the kit's own tests
.github/workflows/qa.yml   runs tests and skill-hub qa on every pull request; builds and deploys on main
.github/workflows/deploy-*.yml  publish the marketplace page to the deploy target in hub.yml
.github/workflows/release.yml  opens release PRs and tags skill releases
.github/workflows/kit-update.yml  opens a pull request for each new kit release
.skill-hub/kit.yml         which kit release your hub is on (skill-hub update maintains it)
KIT.md                     this manual
release-please-config.json     which skills Release Please versions (skill-hub new-skill adds to it)
.release-please-manifest.json  each skill's last released version (Release Please maintains it)
.claude-plugin/marketplace.json   lists each skill for Claude Code (generated by skill-hub manifests)
.cursor-plugin/marketplace.json   lists each skill for Cursor (generated by skill-hub manifests)
```

You own `README.md`, `hub.yml`, `skills/` and the two release files, which list your skills. Everything else belongs to the kit, which keeps pulling in kit updates simple (see [Updating your hub](#updating-your-hub)). New config keys are always optional with a default, so your `hub.yml` keeps working.

## Writing a skill

A skill is a folder whose name matches the `name` in its `SKILL.md`:

```markdown
---
name: changelog-formatter
description: "Formats changelog entries. Use when the user asks to write or tidy a changelog."
metadata:
  version: "0.1.0" # x-release-please-version
---

# Changelog formatter

Instructions for the agent go here.
```

The rules QA enforces:

- **Frontmatter keys:** only the six from the Agent Skills spec: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Strict consumers such as claude.ai uploads reject anything else. If your hub only targets Claude Code, you can allow its extra keys (for example `when_to_use`) in `hub.yml` under `qa.allow_keys`.
- **`name`:** 1 to 64 characters of lowercase letters, digits and single hyphens, matching the folder name.
- **`description`:** up to 1024 characters. Say what the skill does and when to use it, since that is how agents decide to load it.
- **Version:** a quoted SemVer string in `metadata.version`. A top-level `version` key is not part of the spec and fails QA. Keep the `# x-release-please-version` marker on that line: Release Please bumps the version there.
- **Secrets:** every file in a skill, hidden files included, is scanned for known token shapes and credential assignments. For a deliberate example in documentation, put `skill-hub: allow-secret` on that line.

`skill-hub new-skill` refreshes the marketplace manifests. After you edit a skill's description, change `name`, `owner` or `description` in `hub.yml`, or add or remove a skill by hand, run `uv run skill-hub manifests`; QA (R7) fails until you do.

## Releasing a skill

Each skill has its own version, bumped by [Release Please](https://github.com/googleapis/release-please) from your commit messages:

- `fix:` bumps the patch version, `feat:` the minor, and a breaking change (`feat!:` or a `BREAKING CHANGE:` footer) the major. To force a version, add a `Release-As: 1.0.0` footer.
- A commit counts toward a skill when it changes files in that skill's folder.

On every push to `main`, the release workflow opens or updates one release PR. Merging it bumps each changed skill's `metadata.version`, writes its `CHANGELOG.md`, and tags the release `<skill>-v<version>`. A skill's first release is `0.1.0`, whatever its `metadata.version` says. If you bring in a skill that is already at a higher version, add a `Release-As: <that version>` footer to a commit that changes it before its first release; QA warns (S16) until that first release.

Before your first release:

1. **Let Actions open pull requests.** In your repository, go to Settings → Actions → General and turn on "Allow GitHub Actions to create and approve pull requests".
2. **Optional: run QA on release PRs.** A PR opened with GitHub's default token does not trigger other workflows, so QA runs on `main` after the release PR merges, not on the PR. If you require checks before merging, create a fine-grained personal access token (or a GitHub App token) with contents and pull-request write access, and save it as the `RELEASE_PLEASE_TOKEN` Actions secret.

`skill-hub new-skill` registers each new skill in `release-please-config.json`. To opt out of releases, delete `release-please-config.json` and `.release-please-manifest.json`; QA then skips its release checks.

## Marketplace page

`uv run skill-hub build` checks the hub with QA, then writes the marketplace page into `site/`: an `index.html` with a card for every skill and a search box, plus `catalog.json`. Any QA error stops the build; warnings don't. Upload the folder to any static host, or let CI publish it (see [Deploying the marketplace page](#deploying-the-marketplace-page)). CI builds it on every push to `main` and attaches it to the workflow run as the `marketplace-page` artifact. Use `--out PATH` to write elsewhere. The build only replaces a folder it created itself, so it refuses to write into a folder that holds anything else.

Restyle the default page from `hub.yml`:

```yaml
site:
  accent: "#4f46e5"   # hex colour for links and highlights; keep the quotes
  logo_url: "https://example.com/logo.png"   # or a path relative to the page
  theme: ""           # your own theme folder; empty = the built-in default
```

The default page is one file with its styles inlined and no outside requests, so it works offline and on locked-down hosts. It follows the visitor's light or dark setting, and with JavaScript off it shows every card without the search box.

### Catalog format

`catalog.json` is the contract every theme renders from. Version 1:

```json
{
  "schema_version": 1,
  "hub": {"name": "...", "display_name": "...", "owner": "...", "description": "...", "repo_url": "..."},
  "skills": [{
    "name": "...", "description": "...", "version": "1.2.0",
    "license": null, "compatibility": null,
    "links": {"source": "<repo_url>/tree/HEAD/skills/<name>", "changelog": null, "release": null},
    "install": {"claude_code": "...", "gh_skill": "..."}
  }]
}
```

Skills are sorted by name. `install` is `null` unless `repo_url` is a `https://github.com/<owner>/<repo>` URL, and `gh_skill` is `null` until the skill's first release. `license` and `compatibility` are `null` when the skill doesn't set them. `changelog` links to the skill's `CHANGELOG.md` when it has one, and `release` links to the `<name>-v<version>` release once Release Please has published one. New fields may be added within version 1; a breaking change bumps `schema_version`.

### Custom themes

A theme is a folder with an `index.html.j2` [Jinja2](https://jinja.palletsprojects.com/) template. To make your own, copy `skill_hub/themes/default/` into your hub (for example to `theme/`), set `site.theme: "theme"` in `hub.yml`, and edit it.

- `index.html.j2` renders to `index.html`. Other `*.j2` files are partials it can `{% include %}`; they're not copied.
- Every other file (CSS, images, fonts) is copied as-is, keeping its subfolders. Dot-files are skipped, and symlinks are skipped with a warning.
- The template receives `catalog` (the data in `catalog.json`) and `site` (`accent` and `logo_url` from `hub.yml`).
- Every value is HTML-escaped automatically, so skill text can't inject markup. An undefined variable fails the build with the file and line, instead of rendering blank.
- A theme can't contain its own `index.html` or `catalog.json`, and it must sit inside the hub.

## Deploying the marketplace page

On every push to `main`, CI builds the marketplace page and publishes it to the deploy target `hub.yml` names. Pull requests never deploy. A new hub starts with `target: ""`, so its deploy jobs show as skipped and the run stays green until you pick one.

```yaml
deploy:
  target: s3              # "", github-pages, s3, rsync, or your own
  s3:
    bucket: "acme-skills"
    endpoint: ""          # empty = AWS; set for R2, MinIO or B2
    region: "us-east-1"
```

Each target is one workflow file, `.github/workflows/deploy-<target>.yml`, called from a short job in `qa.yml`. Every deploy ships the exact `marketplace-page` artifact the build job produced, and each job receives only its own target's secrets. QA checks the `deploy:` block (H12 to H16) without printing its values, and `uv run skill-hub deploy-config` prints what CI will pass to the deploy job.

| Target | Settings in `hub.yml` | Actions secrets | One-time setup |
|---|---|---|---|
| `github-pages` | none | none | Under **Settings → Pages**, set **Source** to **GitHub Actions** |
| `s3` | `bucket` and `region`, plus `endpoint` for anything other than AWS | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | A bucket served as a static site (directly or behind a CDN) and a key that can write to it. For Cloudflare R2, set `endpoint` to `https://<account-id>.r2.cloudflarestorage.com` and `region` to `auto` |
| `rsync` | `host`, `user` and `path`, plus `port` if it isn't 22 | `DEPLOY_SSH_KEY` (a private key), `DEPLOY_SSH_KNOWN_HOSTS` (the server's lines from `ssh-keyscan -p <port> <host>` (one per key type), after you check their fingerprints; with a port other than 22 each line starts `[host]:port`) | A web server that serves `path`, with the key's public half in the user's `authorized_keys` |

The `s3` and `rsync` targets delete anything at the destination that isn't in the build, so point them at a bucket or folder that holds only the marketplace page.

You don't need to remove the targets you don't use: their jobs are skipped. If you do remove one, delete its workflow file and its job in `qa.yml` together, because GitHub rejects the whole workflow when a job calls a file that doesn't exist.

### Your own deploy target

1. Copy `.github/workflows/deploy-rsync.yml` to `deploy-<name>.yml` and change its inputs, secrets and deploy step.
2. Copy the `deploy-rsync` job in `qa.yml`, rename it, and change its `if:` to `needs.build.outputs.target == '<name>'`, its `uses:` path, its `with:` values (write your target's settings there) and its `secrets:`.
3. Set `deploy.target: <name>` in `hub.yml`.

QA checks that the workflow file exists, but not the settings a custom target reads. Your edit to `qa.yml` is the one change to a kit-owned file, so expect to merge it when you pull kit updates.

### Previewing locally

```bash
uv run skill-hub build
python -m http.server -d site
```

Then open http://localhost:8000.

## Installing skills

Every install path reads the hub straight from its GitHub repository, so nothing needs publishing. Replace `<owner>/<repo>` with the hub's repository and `<hub-name>` with `hub.name` from `hub.yml`. The marketplace page shows each skill's commands ready to copy.

**Claude Code.** Add the hub once, then install any skill:

```
/plugin marketplace add <owner>/<repo>
/plugin install <skill>@<hub-name>
```

From a shell, `claude plugin install <skill> --marketplace <owner>/<repo>` does both in one step. Each skill is its own plugin, so you install only what you want, and updates arrive with new commits.

**GitHub Copilot.** Use the GitHub CLI and pin the skill's release tag:

```
gh skill install <owner>/<repo> <skill>@<skill>-v<version>
```

Pin the tag: without it, `gh skill` installs from the repository's latest release, which in a hub can belong to a different skill. Add `--agent cursor`, `--agent codex` or another agent name to install for that agent instead, and `--scope user` to install for every project.

**Cursor.** Open Customize, then Plugins, then From GitHub Repository, and enter `<owner>/<repo>`. Cursor reads `.cursor-plugin/marketplace.json` and lists each skill as a plugin.

**Other agents.** `gh skill install` supports many agents through `--agent`. Vercel's skills CLI also works: `npx skills add <owner>/<repo> --skill <skill>`.

**Private hubs.** Every path uses your existing git credentials, an SSH key or `gh auth login`, so a private hub works for anyone who can clone it. Claude Code's background auto-update needs a stored credential, such as `gh auth setup-git`.

**Scripts.** A skill's bundled scripts run with whatever is installed on the developer's machine; nothing installs their dependencies.

The generated commands on the marketplace page need `repo_url` to be a `https://github.com/<owner>/<repo>` URL. For other hosts the page shows no commands, and the paths above still apply with your host's clone URL where the client supports it.

## Updating your hub

The kit ships new releases, tagged `kit-v<version>` in the kit repository named in `.skill-hub/kit.yml`. Your hub receives each one as a pull request. `.skill-hub/kit.yml` records the release your hub is on, so the updater knows what changed in the kit and what you changed yourself.

### How an update PR works

The "Kit update" workflow (`.github/workflows/kit-update.yml`) runs every Monday and can be run by hand from the Actions tab. When the kit has a newer release in the same major version, it opens one pull request, labelled `kit-update`, from the branch `kit-update/v<version>`. The PR body lists the changelog, the files changed, the files left alone and why, and the QA result.

- **One update at a time.** While an update PR is open the workflow leaves it alone. If a newer release appears meanwhile, it adds one comment to the open PR. Merge or close the PR and the next run proposes the newest release.
- **Closing a PR declines that version.** Close an update PR without merging and the workflow never reopens it; it waits for a newer release.
- **A new major release is opt-in.** A major release can contain breaking changes, so the weekly run does not propose it. It opens one issue titled `skill-hub kit <N>.x is available` instead. To take it, run the "Kit update" workflow by hand with the `major` box ticked, or run `uv run skill-hub update --major` locally and open the PR yourself.
- **Scheduled runs can switch off.** GitHub disables scheduled workflows in a public repository after 60 days without activity. Re-enable "Kit update" from the Actions tab. A manual run always works.

You can also update from your own machine, with a clean working tree:

```bash
uv run skill-hub update --check   # report the target release, change nothing
uv run skill-hub update           # merge it into the working tree; never commits
```

Review the changes, commit them and open a PR as usual. `update` also rewrites `.skill-hub/kit.yml`, regenerates the marketplace manifests, regenerates `uv.lock` with `uv lock` when the kit's lock file or `pyproject.toml` changed, and ends with a QA count.

### Resolving conflicts

The updater does a three-way merge per file: the kit release you were on, the new kit release, and your copy. A file you didn't touch is replaced. A file only you changed is kept. When both of you changed the same lines, the file gets git conflict markers (`<<<<<<< your hub`, `=======`, `>>>>>>> kit (new)`) and appears under "Conflicts" in the PR body. The update PR is committed with the markers in place, so resolve them before you merge. To resolve one:

1. Check out the PR branch (`git fetch && git switch kit-update/v<version>`).
2. Open each file listed under "Conflicts", keep the lines you want and delete the markers.
3. Run `uv run skill-hub qa`, then commit and push to the same branch.

The "Files left alone" list gives the reason for each file the updater kept as yours, such as "the hub deleted this file and the kit changed it", a symlink or submodule in the way, or a binary file both sides changed. Look at those by hand if you want the kit's version.

### Approving checks on the PR

A PR opened with GitHub's built-in token doesn't start your checks on its own. Open the PR and click "Approve and run" to start them. With `KIT_UPDATE_TOKEN` (below), the checks start by themselves.

### Repository setting

Turn on Settings → Actions → General → "Allow GitHub Actions to create and approve pull requests". Without it the workflow fails when it tries to open the PR, and says so in its log. This is the same setting the release workflow needs.

### The optional `KIT_UPDATE_TOKEN`

GitHub does not let the built-in token change files under `.github/workflows/`. Without a token, the update PR leaves those files out and records them as pending in `.skill-hub/kit.yml`. QA then warns with H17 until you apply them:

```bash
git fetch && git switch kit-update/v<version>   # the update PR's branch, or main after you merge it
uv run skill-hub update --workflows-only
git add -A && git commit -m "chore: update kit workflow files" && git push
```

`--workflows-only` merges the held-back workflow files the same way as a full update, clears the pending record, and cannot be combined with `--major`, `--skip-workflows` or `--check`.

To have the PR include workflow files and start its checks without approval, create a token and save it as the Actions secret `KIT_UPDATE_TOKEN`. Either of these works:

- **A fine-grained personal access token** limited to your hub repository, with read and write access to Contents, Pull requests, Issues and Workflows.
- **A GitHub App token** with the same four permissions.

### Which updater runs

The workflow runs your hub's own `skill-hub`, from the code already in your repository and locked by `uv.lock`, never code from the release it is fetching. That keeps what runs reviewed by you. The consequence: a fix to the updater itself reaches your hub in one update and takes effect from the next one.

### What an update never touches

- `README.md`, `skills/`, `release-please-config.json` and `.release-please-manifest.json`, which are yours.
- The two marketplace manifests, which are regenerated from your skills and `hub.yml` rather than merged.
- Anything the kit doesn't ship, such as your own themes or extra workflows.

`uv.lock` is regenerated with `uv lock` when needed instead of being merged. A file you deleted stays deleted. One known limit: if you deleted a file, the kit later removed it, and a still later release brings it back, it returns as a new file.

## Maintaining the kit

This section is for the people who publish kit releases. Hubs can skip it.

- **Mark the kit repository.** Set the repository variable `SKILL_HUB_KIT_RELEASES` to `true` (Settings → Secrets and variables → Actions → Variables). It turns on the kit's own Release Please stream, which tags `kit-v<version>`, and switches off the update workflow, which would have nothing to update from.
- **Protect the tags.** Add a tag ruleset for `kit-v*` that blocks updates and deletion. Hubs check that a release tag still points at the commit they recorded, and stop if it moved.
- **Keep `main` releasable.** A hub created between releases records the last release, so what is on `main` reaches that hub's first update.
- **Remove `release-as` after `kit-v1.0.0`.** `kit-release-please-config.json` pins the first release with `release-as`. Once `kit-v1.0.0` is cut, remove that key and update `test_kit_package_shape`, which asserts it, in the same commit. `test_release_as_is_removed_after_first_release` fails until you do.
- **A root-only commit still bumps the kit.** Release Please can only exclude folders, so a `feat:` or `fix:` commit that touches only root-level hub-owned files (`README.md` or the release-please files) still bumps the kit version.

## QA checks

`uv run skill-hub qa` prints one line per finding and exits non-zero on any error. Add `--strict` to fail on warnings too, or `--root PATH` to check another hub. Findings never print the value that triggered them, so a leaked secret doesn't end up in your CI logs.

| ID | Checks | Level |
|---|---|---|
| H1 | `hub.yml` exists and is a regular file | error |
| H2 | `hub.yml` is UTF-8, valid YAML (no duplicate or merge keys) and a mapping | error |
| H3 | `hub.name`, `display_name`, `owner`, `description` and `repo_url` are filled in (`owner` and `description` can be written as UTF-8) | error |
| H4 | `hub.name` uses lowercase letters, digits and single hyphens | error |
| H5 | `qa` is a mapping and `qa.allow_keys` is a list of strings | error |
| H6 | `hub.name` or `repo_url` is still the kit's default | warning |
| H7 | `site` is a mapping and `accent`, `logo_url` and `theme` are strings (an unknown key under `site` is a warning) | error |
| H8 | `site.accent` is a hex colour such as `"#4f46e5"` | error |
| H9 | `site.logo_url` is an `https://` URL or a relative path | error |
| H10 | `site.theme` is a folder inside the hub root that contains `index.html.j2` | error |
| H11 | `hub.name` is not a marketplace name Claude Code reserves (such as `agent-skills`, `github` or anything starting `claudeai-`) | error |
| H12 | `deploy` is a mapping and `deploy.target` is empty or a name of a-z, 0-9 and single hyphens (an unknown key under `deploy` is a warning) | error |
| H13 | `deploy.s3` and `deploy.rsync` are mappings, their settings are strings, and `port` is a number (an unknown key in either is a warning) | error |
| H14 | The chosen target has its required settings: `s3` needs `bucket` and `region`; `rsync` needs `host`, `user` and `path` | error |
| H15 | Every filled-in deploy setting, for any target, has a safe value (such as a valid bucket name, an `https://` endpoint, or a path with no shell characters that names a folder below `/` or `~`) | error |
| H16 | A non-empty `deploy.target` has a matching `.github/workflows/deploy-<target>.yml` | error |
| H17 | `.skill-hub/kit.yml`, if present, can be read and has no workflow files held back by an update | warning |
| S1 | The skill has a `SKILL.md` | error |
| S2 | `SKILL.md` is UTF-8 and opens with a `---` frontmatter block | error |
| S3 | The frontmatter is valid YAML and a mapping | error |
| S4 | `name` is valid and matches the folder | error |
| S5 | `description` is present, at most 1024 characters and can be written as UTF-8 | error |
| S6 | No top-level keys outside the spec (and `qa.allow_keys`) | error |
| S7 | `metadata.version` is a quoted SemVer string | error |
| S8 | `metadata`, `compatibility`, `license` and `allowed-tools` have the right types and lengths | error |
| S9 | Every `.py` file compiles | error |
| S10 | No secrets in any file of the skill | error |
| S11 | `SKILL.md` has instructions after the frontmatter | warning |
| S12 | Symlinks and non-regular files are skipped | warning |
| S13 | A file or folder in the skill could not be read | error |
| S14 | `description` is still the placeholder written by `skill-hub new-skill` | warning |
| S15 | `metadata.version` matches the skill's manifest entry, and its `version.txt` if it has one | error |
| S16 | A registered skill that has never been released has a `metadata.version` other than its first-release version (`initial-version`), which the first release would overwrite | warning |
| S17 | The skill's name doesn't pass for one of Anthropic's own plugins (such as a `claude-` or `anthropic-` prefix), which Claude Code's plugin validator rejects | warning |
| S18 | The skill's name is not `kit`, which the kit keeps for its own release tags | error |
| R1 | `skills/` exists and can be read | error |
| R2 | `skills/` holds at least one skill | error |
| R3 | A loose file sits directly in `skills/` | warning |
| R4 | A symlink sits directly in `skills/` | warning |
| R5 | `release-please-config.json` lists every skill under `packages`, `.release-please-manifest.json` exists, and both are JSON objects (skipped when the config is absent) | error |
| R6 | No release config or manifest entry names a path under `skills/` that is not a skill | error |
| R7 | `.claude-plugin/marketplace.json` and `.cursor-plugin/marketplace.json` exist and match what `skill-hub manifests` would write (checked only when nothing else failed) | error |

## Contributing

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `chore:`). These prefixes decide each skill's next version, so pick them with care: `feat` for new behaviour, `fix` for corrected behaviour.

Run `uv run ruff check`, `uv run pytest` and `uv run skill-hub qa` before opening a pull request. CI runs all three. To lint on every commit, install the hook once with `uv run pre-commit install`.

## Prior art

skill-hub borrows ideas from these projects, without sharing code:

- [googleapis/release-please](https://github.com/googleapis/release-please): conventional-commit releases, the versioning engine.
- [ai-plugin-marketplace/tools](https://github.com/ai-plugin-marketplace/tools): a TypeScript toolkit that builds plugin marketplaces for several AI clients. skill-hub stays independent of it, to keep a single config file, a skill-as-folder model, Copilot support and a Python-only toolchain, and borrows its default-name warning and strict name rule.
- [dukelyuu/skills-marketplace](https://github.com/dukelyuu/skills-marketplace): a full-stack skill marketplace app; a reference for what a catalog page should show.
- [WesleySmits/agent-skills](https://github.com/WesleySmits/agent-skills): a skills library with per-client pointer files; a reference for cross-client install patterns.
